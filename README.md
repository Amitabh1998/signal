# Signal

Signal is a software factory: it turns a product request and optional context into a buildable microapp mission, then can hand an accepted mission to an explicitly configured local coding runner that implements, tests, and opens a pull request for review.

RocketRide is an open-source pipeline runtime, not an agent itself. In this project it has two decision workflows:

- `signal-room.pipe` parses the brief and optional files, runs three parallel LLM roles (Customer Advocate, Skeptic, and Product Strategist), synthesizes their output, validates the structured report, and links proof to sources.
- `delivery-review.pipe` runs after a coding run has changed files and passed its configured checks. Change Reviewer, Quality Gatekeeper, and Release Skeptic assess the approved mission, coding summary, diff stat, and recorded command outcomes before a pull request is opened. Its `ready` verdict means ready for **human pull-request review**, never automatic release.

The product is deliberately honest about execution state:

- **Prepare inputs** only displays the literal request and names of staged files. It does not infer requirements, architecture, risks, agent output, or a product plan.
- Only a completed live **Run scope workflow** may produce the scope report used to create a build mission.
- The hosted UI opens with a deterministic **DEMO REPLAY**. It never claims that fixture was generated live.
- Adding files in the browser does **not** fabricate an analysis. The files are marked “not analyzed.”
- A report is called live only when generated by the included RocketRide SDK runner and imported into the UI.
- The UI validates report shape, but it cannot independently prove that an arbitrary imported JSON file genuinely came from RocketRide. It says this explicitly.
- When `data/live-report.json` exists locally, the UI offers **Load latest live run** and explains that it is loading a saved engine result rather than making a new browser-side model call.
- Evidence cards open a source viewer. Runner-produced reports preserve the exact text from each `SOURCE:` section; demo excerpts and browser-staged files are labeled separately.

## Execution: code, tests, and pull requests

Signal does not silently grant browser requests control over your machine. Repository execution is disabled by default. To enable it for one trusted local repository, set:

```bash
SIGNAL_EXECUTION_ENABLED=1
SIGNAL_EXECUTION_REPO=/absolute/path/to/trusted/repository
SIGNAL_EXECUTION_BASE=main
# Keep this separate from any public upstream remote when needed.
SIGNAL_EXECUTION_REMOTE=origin
SIGNAL_DELIVERY_REVIEW_ENABLED=1
# Optional. A delivery-review failure blocks pull-request creation only when this is 1.
SIGNAL_DELIVERY_REVIEW_REQUIRED=0
```

When enabled, the local runner creates an isolated git worktree from `SIGNAL_EXECUTION_REMOTE` and `SIGNAL_EXECUTION_BASE`, dispatches Codex CLI with the approved mission, runs the repository's `npm test` and `npm run build` scripts when available, and optionally sends the resulting delivery bundle to RocketRide. It then commits the tested diff, pushes a `signal/*` branch to that same remote, and opens a GitHub pull request with `gh`. The RocketRide review is added to the PR body when available. It requires a working Codex CLI and authenticated GitHub CLI. Keep this server local and only point it at a repository you explicitly trust.

### Coding-runner connections

Use **Connections** in Signal's top bar to check local Codex and Claude Code authentication. On macOS, **Sign in** opens the runner's official CLI authentication flow in Terminal; credentials remain in the CLI's own local store and are never sent through Signal. Current build dispatch uses Codex CLI. Claude Code can be connected in advance, but it is not presented as an available build runner until its dedicated dispatch integration exists.

## Promise Theory and Semantic Spacetime

Promise Theory is used as an operational contract between pipeline components. Each specialist promises only its own behavior: cite evidence, expose counterarguments, or propose a reversible experiment. The Promise Ledger assesses those promises from returned evidence and traces; it does not treat a prompt as a guarantee.

Semantic Spacetime is represented as a declared topology. Evidence, agents, and decisions become adjacent through explicit `supports` and `challenges` relationships. The map does not claim visual proximity or an embedding proves causality.

This is an applied product interpretation of Mark Burgess and Jan Bergstra's work, not a new formalization. Primary background: [Promise Theory](https://markburgess.org/promises.html) and [Promise Theory: Principles and Applications](https://markburgess.org/BookOfPromises.pdf), especially the discussion of autonomous agents, assessments, adjacency, and Semantic Spacetime.

## Run the interface

```bash
npm install
npm run dev
```

Open `http://127.0.0.1:4173`. Use **Guided tour** at any time, or open
`http://127.0.0.1:4173/?tour=1` to start the seven-step walkthrough automatically.

The local dev server also exposes `POST /api/analyze`. In the UI, **Run RocketRide**
uses that endpoint to call the included runner and load the resulting report. If the
engine is not configured or the run fails, Signal Room does not substitute demo
output.

## Demo flow

Use the first screen for the clearest demo:

1. Write a mission brief.
2. Optionally add context with the **+** button.
3. Click **Run scope workflow** to send the brief and context to RocketRide.
4. Review the decision, proof, commitments, and trace.
5. Click **Create build mission**. If local repository execution is configured, use **Run implementation** to dispatch code, tests, and a pull request.

Seed the browser-agent evidence for a live RocketRide run:

```bash
npm run seed:scenario -- --list
npm run seed:scenario -- --scenario browser-workflow-agent
npm run analyze:live -- --input data/seed-evidence.txt --output data/live-report.json
```

Refresh the UI and choose **Load latest live run** to compare the deterministic seed outcome with the live engine result.

## Run a real RocketRide analysis

Requirements:

1. RocketRide Server v3.4.0 reachable locally or in Cloud.
2. The server has `ROCKETRIDE_OPENAI_KEY` available for the five `llm_openai` nodes.
3. `ROCKETRIDE_URI` points at the engine. For Cloud, also set `ROCKETRIDE_APIKEY` or `ROCKETRIDE_AUTH`.

```dotenv
# .env
ROCKETRIDE_URI=ws://localhost:5565
ROCKETRIDE_AUTH=your-local-engine-key
ROCKETRIDE_APIKEY=the-same-local-engine-key
ROCKETRIDE_OPENAI_KEY=your-openai-key
```

```bash
npm run analyze:live -- --input data/sample-evidence.txt --output data/live-report.json
# A delivery bundle is normally created by an enabled implementation run.
npm run delivery-review:live -- --input delivery.json --output data/live-delivery-review.json
```

Refresh the local UI and choose **Load latest live run**. You can also choose
**Import live report** and select any runner-produced JSON report manually.

## Check whether RocketRide is healthy

```bash
npm run rocketride:check
```

This performs an authenticated engine connection and ping, validates the real
scope and delivery-review pipelines on the server, and checks the last scope
report's contract. It prints
`RocketRide health: PASS` only when the engine and pipeline checks succeed. The
local UI displays the timestamped result; an old successful check is labeled as
historical rather than being presented as current health.

The runner requests `pipelineTraceLevel: "summary"`, refuses to create a fallback report when the engine fails, and cleans up the task token before disconnecting.

## Pipeline

[`pipelines/signal-room.pipe`](./pipelines/signal-room.pipe) is a real RocketRide pipeline:

```text
evidence → parse → question
                   ├─ customer advocate ─┐
                   ├─ skeptic ───────────┼─ evidence reconciliation → JSON contract enforcement → decision JSON
                   └─ product strategist ┘
```

The three specialist LLM nodes fan out concurrently. Their answers are converted to documents and joined by the synthesis prompt. RocketRide's native `extract_data` node then invokes a formatter LLM with `expectJson=true`, validates the response, and retries malformed JSON before the result reaches the runner. Every model instruction forbids invented facts and requires uncertainty when evidence is insufficient.

The optional delivery workflow follows the same durable pattern:

```text
tested delivery bundle → parse → question
                              ├─ change reviewer ───┐
                              ├─ quality gatekeeper ┼─ delivery reconciliation → JSON contract enforcement → review JSON
                              └─ release skeptic ───┘
```

## Verification

```bash
npm test
npm run eval
npm run build
```

`npm run eval` checks the hackathon-critical trust contract: proof claims must point
to real sources, proof quotes must appear in embedded source text when available,
signals must not be orphaned from source labels, and skeptical evidence must cap
confidence below absolute certainty.

## Current limits

- This repository does not bundle the RocketRide engine. The integration has been validated against local RocketRide Server v3.4.0.36.
- `data/live-report.json` is deliberately gitignored because live outputs are local runtime artifacts.
- The first version accepts a combined text evidence bundle. PDF/image OCR is a natural next step, but is not falsely advertised as complete here.
- Promise assessments currently come from the structured result and summarized trace contract. A deeper version should reconcile them directly against RocketRide's recorded per-object trace API.
